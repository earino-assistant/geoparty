# GeoParty: Build Specification

## Thesis

GeoParty is a Jackbox-style geoguessing party game. One person (the operator) drives street-level imagery from their phone. Everyone else watches a TV showing a clean spectator view of the same imagery and shouts suggestions. The operator drops a guess on a map, the TV reveals the true location, and points are awarded by distance. The entire system is static JavaScript on GitHub Pages, synced through Firebase Realtime Database. There is no server code, no build step, and no cost.

This document is a complete, self-contained handoff. All tokens and config are real and inlined. A coding agent should be able to build, test against the live Firebase database, and ship without asking the owner for anything except the final GitHub repo push.

## 1. Architecture and constraints

**Hard constraints:**

- Static hosting only. Everything ships as HTML/CSS/JS files served by GitHub Pages.
- No build tooling. No bundler, no npm, no transpilation. Use native ES modules and CDN imports so the repo is directly deployable and hackable. Pin CDN versions.
- No server code anywhere. Firebase Realtime Database (Spark free plan) is the only stateful dependency, accessed directly from the client SDK.
- Phone-first operator UI. The /host view must be fully usable one-handed on a mobile browser (iOS Safari and Android Chrome).
- TV display is a plain URL. The /screen view must work in any modern browser so it can reach the TV via Chrome tab casting, a smart TV browser, or a Fire Stick. No Cast SDK.

**Libraries (all via CDN, pinned):**

- MapillaryJS 4.x for street imagery (https://unpkg.com/mapillary-js@4.1.2/dist/mapillary.js and .css)
- Leaflet 1.9.x with OpenStreetMap tiles for the guess map and reveal map (include the standard OSM attribution)
- Firebase JS SDK 10.x, modular, via https://www.gstatic.com/firebasejs/ CDN imports (app + database only)
- No other dependencies. No jQuery, no framework. Vanilla JS with small modules.

**Sync model:** the host is the single source of truth. The host writes the full game state to `rooms/{roomCode}` in Firebase. The screen is a pure subscriber that renders whatever state it receives. The screen never writes game state (it writes only its own presence heartbeat). This one-way flow eliminates conflict resolution entirely.

**Imagery sync:** do not stream camera pose deltas at high frequency. On each frame the operator moves, throttle pose writes (image ID, bearing, and MapillaryJS viewer state) to at most 4 writes/second. The screen runs its own MapillaryJS viewer and applies the received image ID and pose. Slight TV lag is acceptable and expected.

## 4. Data model (Firebase)

Everything lives under `rooms/{roomCode}`. Room codes are 4 uppercase letters, generated by the host, excluding ambiguous characters (no I, O). Full shape:

```json
{
  "rooms": {
    "KWPF": {
      "createdAt": 1755600000000,
      "phase": "lobby | roundActive | guessing | reveal | gameOver",
      "settings": {
        "roundCount": 5,
        "roundSeconds": 120,
        "moveAllowed": true
      },
      "round": {
        "number": 2,
        "imageId": "1234567890123456",
        "startedAt": 1755600030000,
        "endsAt": 1755600150000,
        "pose": { "bearing": 214.5 },
        "truth": null,
        "guess": null,
        "score": null
      },
      "teams": {
        "t1": { "name": "Couch Left", "total": 8450 },
        "t2": { "name": "Couch Right", "total": 7900 }
      },
      "activeTeam": "t1",
      "screenHeartbeat": 1755600140000
    }
  }
}
```

Key decisions:

- `round.truth` (the answer coordinates) is written by the host only at reveal time, never before. This keeps the answer off the wire while spectators could theoretically open dev tools on the screen page.
- `round.imageId` alone is what the screen needs to render imagery; MapillaryJS resolves everything else from the ID.
- Timer authority is the host's clock via `endsAt` (epoch ms). The screen renders countdown from `endsAt` minus its own clock. Do not tick the timer through Firebase.
- Teams are optional. Default is a single team named "Everyone". Support 1 to 4 teams, rotating `activeTeam` each round if more than one.

## 5. Firebase security rules

Paste these in the Firebase console (Realtime Database, Rules tab) and note them in the README. They scope the open database to room paths, validate the shape, and let anyone clean up rooms older than 24 hours.

```json
{
  "rules": {
    ".read": false,
    ".write": false,
    "rooms": {
      "$roomCode": {
        ".read": true,
        ".write": "!data.exists() || data.child('createdAt').val() > (now - 86400000) || newData.val() == null",
        ".validate": "$roomCode.matches(/^[A-HJ-NP-Z]{4}$/)",
        "createdAt": { ".validate": "newData.isNumber() && newData.val() <= now" }
      }
    }
  }
}
```

This is deliberately permissive within `rooms/`. It's a party game with public client credentials; the threat model is drive-by vandalism, not adversaries. The rules prevent writes outside room paths, enforce room code format, and allow deletion of stale rooms. Accept the residual risk and say so in the README.

## 6. The two views

### /host (phone controller)

Screens, in order:

1. **Setup.** New game button. Settings: rounds (3/5/10), seconds per round (60/120/180/no limit), movement allowed toggle (movement off is "no moving" mode, harder), team count and names. Creates room, writes initial state, shows the room code huge, plus the screen URL and a QR code for it (generate the QR client-side, any tiny MIT-licensed QR lib inlined is acceptable as the single exception to the no-dependency rule, or draw it with a canvas QR implementation).
2. **Lobby.** Shows "waiting for screen" until `screenHeartbeat` appears, then a Start Round button.
3. **Round.** Full-bleed MapillaryJS viewer the operator pans/moves. Overlay: round number, countdown, and a prominent "Make Guess" button. If movement is disabled in settings, lock navigation (MapillaryJS component options) but allow pan/zoom.
4. **Guess.** Leaflet world map. Tap to place pin, drag to adjust, confirm button. On confirm the host computes distance and score locally, writes `truth`, `guess`, `score`, and `phase: "reveal"`.
5. **Reveal.** Shows distance, points this round, running totals. Next Round button (or Finish after the last round).
6. **Game over.** Final standings, "Save to leaderboard" (see section 10), New Game button.

The operator's phone stays in this flow the whole evening. Design for thumb reach: primary action always bottom center.

### /screen (TV display)

One page that renders based on `phase`:

- **Waiting.** Big room code entry (4-letter input, TV-remote friendly: also accept `?room=KWPF` in the URL so the QR from the host encodes it and no typing is needed). Once subscribed, writes `screenHeartbeat` every 10s.
- **Lobby.** Game title, team names, "waiting for operator".
- **Round.** Full-screen MapillaryJS viewer mirroring the host's image and pose, with a big countdown, round number, and active team name. No controls whatsoever. This is the view the party stares at.
- **Reveal.** Split view: Leaflet map with truth pin, guess pin, a line between them, auto-fit bounds, distance and points animated in large type. Then running scoreboard.
- **Game over.** Podium with team standings, confetti (CSS only, keep it cheap).

The screen is display-only. It never accepts input after room entry.

## 7. Game flow state machine

Phases and legal transitions, enforced in `game.js` and driven exclusively by host writes:

```
lobby -> roundActive        (host taps Start Round; host samples pool, writes imageId, endsAt)
roundActive -> guessing     (host taps Make Guess, or timer expires on host)
guessing -> reveal          (host confirms pin; host writes truth/guess/score)
reveal -> roundActive       (host taps Next Round, rounds remaining)
reveal -> gameOver          (host taps Finish, or last round completed)
gameOver -> lobby           (host taps New Game; new room code, fresh state)
```

Timer expiry is detected on the host (it owns `endsAt`). On expiry, force transition to guessing with a "time's up" toast. If the operator hasn't guessed 60 seconds into guessing, no penalty, just wait; parties are chaotic.

## 8. Scoring

GeoGuessr-style exponential decay. With distance d in km:

```
score = round(5000 * exp(-d / 1492))
```

Perfect pin is 5000, ~1500km is about 1800 points, antipodal is effectively 0. Compute great-circle distance with the haversine formula (implement inline, ~10 lines, no dependency). Display distance as km with one decimal under 100km, integer km above.

## 9. Location pool

The repo ships with `data/location_pool.json`, generated by `tools/build_location_pool.py` (provided alongside this spec; include it unmodified). Format per entry:

```json
{
  "image_id": "1234567890123456",
  "lng": 4.8952,
  "lat": 52.3702,
  "viewer_url": "https://www.mapillary.com/app/?pKey=...",
  "thumb": "https://..."
}
```

Build tasks for the agent:

1. Run the generator with `--count 200 --mode weighted` to produce the shipped pool (requires only `pip install requests`; the Mapillary token is already in the script).
2. `pool.js` loads the JSON, shuffles once per game (Fisher-Yates seeded from the room code so a rejoining screen sees the same order), and samples without replacement across rounds.
3. `truth` coordinates come from the pool entry, not from a Mapillary API call at reveal time.
4. If MapillaryJS fails to load a pool image at round start (deleted imagery happens), the host auto-skips to the next pool entry silently and logs to console.

## 10. Persistent leaderboard

Scope: persistence across an evening and between evenings on the same host phone. Implementation: `localStorage` on the host device, key `geoparty_leaderboard`, an array of `{teamName, totalScore, rounds, date}` appended at game over when the operator taps Save. The host setup screen shows an all-time top 10. No sync, no accounts. Mention in the README that clearing browser data clears history.

## 11. Visual design direction

Party-room aesthetic, readable from a couch at 4 meters:

- Screen view typography is enormous: countdown and scores at 8 to 15vh. High contrast, dark background (#111) with a single accent color per team.
- No UI chrome on the screen during rounds except countdown, round, and team name in the corners. The imagery is the show.
- Host view is utilitarian and dense. It's a controller, not a poster.
- Reveal moment is the emotional peak: animate the guess-to-truth line drawing over ~1s, then count the score up. Get this beat right.
- System font stack. No webfonts.

## 12. Edge cases and failure handling

- **Host refresh or phone sleep.** On load, host.html checks localStorage for `geoparty_active_room`; if the room exists in Firebase and is under 24h old, offer Resume, which reattaches as authority for that room.
- **Screen refresh.** Re-enter via URL param, resubscribe, rendering resumes from current state. Stateless by design.
- **Two hosts, same room.** Last write wins and that's fine. Don't build locking.
- **Firebase unreachable.** Both views show a small "reconnecting" pill using the SDK's `.info/connected`. The host can keep playing locally in a degraded single-screen mode (viewer plus guess map on the phone) so the party survives a network hiccup.
- **Mapillary rate limiting (429).** Only plausible during pool generation, not gameplay. Gameplay makes no Mapillary REST calls; MapillaryJS tile/image fetches are well within limits.
- **Stale rooms.** On host setup screen load, delete any `rooms/*` older than 24h that the rules permit removing (best-effort janitor, wrapped in try/catch).

## 13. Deployment

1. Create public GitHub repo `geoparty` under the owner's account (earino-assistant).
2. Push the static site to `main`, root directory.
3. Settings, Pages, deploy from branch `main`, root. Site serves at `https://earino-assistant.github.io/geoparty/`.
4. All asset paths must be relative so the repo-subpath serving works.
5. Paste the security rules from section 5 into the Firebase console Rules tab and publish.
6. Smoke test per section 14 on a phone plus a cast tab.

No CI, no actions, no custom domain.

## 14. Acceptance criteria

The build is done when all of the following pass:

1. Opening `/host` on a phone creates a room and displays code plus QR within 3 seconds.
2. Opening `/screen?room=CODE` on a laptop, then casting that tab to a Chromecast, shows the lobby within 5 seconds of the heartbeat.
3. Starting a round shows the same Mapillary pano on both devices; panning on the phone visibly pans the TV within ~500ms.
4. Movement-disabled mode prevents navigation on both views but allows look-around.
5. Timer expiry on the host forces the guess map open.
6. Confirming a guess triggers the reveal animation on the TV with correct distance (verify one known pair against an online haversine calculator) and correct exponential score.
7. A 5-round game completes with correct running totals and a game-over podium.
8. Saving at game over persists to the leaderboard and survives a host page reload.
9. Killing and reopening the host mid-round offers Resume and successfully reattaches.
10. The screen page never writes anything to `rooms/{code}` except `screenHeartbeat` (verify in the Firebase console data view).
11. A write attempt outside `rooms/` from the browser console is rejected by rules.
12. Everything works served from `https://earino-assistant.github.io/geoparty/` with zero console errors on load.

## Out of scope (do not build)

Player phones joining as guessers, accounts, audio, chat, spectator voting, Cast SDK receiver, server-rendered anything, analytics. The soul of this game is one driver and a loud couch. Keep it that way.
