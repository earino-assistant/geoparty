## The concept: "Flag Reveal" (working title)

A flag-guessing party game for a family/group around a TV, each with a phone. Static no-build GitHub Pages + Firebase RTDB, no server code — same constraints as GeoParty.

**Core loop:** a flag is revealed progressively (tile grid de-occluding + blur→sharp track, ~8 steps). Players ring in on their phones; first *correct* ring wins the round. A wrong ring locks that phone out for the round (private — no other phone or the TV learns it). Round busts (zero points) if all steps + grace elapse with no correct answer.

**Scoring:** earlier = more. `points = BASE × (STEPS − stepAtRing + 1) / STEPS`, floored at MIN. No speed-within-step bonus — the reveal step IS the clock (keeps it clock-skew-immune).

**Win:** first to TARGET points, or highest after roundCount flags.

## Hard product constraints (owner decisions, 2026-08-23)

1. **The TV must ALWAYS be connectable, in BOTH modes** (couch AND everyone-plays). A flag game is a "look at the big screen" game — the TV-connected path is PRIMARY; the "each phone renders its own reveal" path is the fallback for when no TV is available. TV is a first-class, always-available surface, never couch-only.
2. **TV stays a passive renderer** — it only writes `screenHeartbeat`, no new authority role. A host phone owns the reveal timer and writes the current step to RTDB; the TV renders whatever step is current. TV connects simply by subscribing to the room.
3. **Host rotation:** follow the GeoParty model — whoever wins the previous game (of multiple rounds) becomes host for the next round. This is exactly the existing `hostTeam` rotation in h2h mode. Winner's phone owns the reveal timer; TV stays passive throughout.

## The novel concurrency problem (the point of the exercise)

GeoParty's write-ownership model is "writers never contend on the same path" (disjoint-path last-write-wins + one settlement race). A buzzer game breaks this: N phones race ONE path with **first-wins** semantics. The design position is an **RTDB transaction (compare-and-set)** on a single per-round path (`round/buzz/{n}`), which the server serializes — authoritative, clock-skew-immune. This is GeoParty's existing `claimTeamSlot` transaction generalized to per-round.

**This is the key extraction finding to validate:** the kernel needs a first-class **claim/arbitration primitive** as a peer concept to the disjoint-path model. Also new: **private per-phone state** (wrong ring / lockout never mirrored live) — GeoParty has zero hidden information, so the kernel needs an explicit "private subtree, never on the live feed" contract.
